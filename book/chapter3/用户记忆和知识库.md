# 第三章学习路线：用户记忆和知识库

## 一、第三章学习目标

从第三章开始，正式进入 Agent 的**长期记忆与外部知识获取能力**建设。

前两章主要解决：

-   第一章：Agent 是什么，如何通过 LLM、上下文和工具形成 Agent。
-   第二章：如何管理上下文，包括消息结构、Token 预算、上下文压缩等。
-   第三章：如何让 Agent 跨越单次对话，在不同会话之间保留信息，以及如何从企业知识库中获取可靠知识。

本专题采用已确认的**精简学习模式**，以实践驱动学习。每个知识点原则上按三个环节推进：

**快速理解 → 动手实践 → 验证总结。**

讲解尽量合并，实验步骤尽量一次提供所需的完整代码；保留书籍原始顺序、实验范围和必要验证，不因精简而跳过准入条件。具体协作约定见仓库根目录 `AGENTS.md`。

核心原则：

> 不是为了使用 LangGraph、向量数据库或者 RAG
> 而引入它们，而是先确定书中要解决的问题，再选择对应的技术实现。

学习路线以《深入理解 AI
Agent》第三章"用户记忆和知识库"为依据。具体实施时，应先核对书中对应章节、理论和实验，再决定工程设计，避免凭经验随意扩展架构。

## 二、第三章的知识结构

第三章可以按三个相互关联的部分学习。

### 2.1 用户记忆系统

- 记忆能力的三层次评估
  - 放哪里？
  - 怎么存？
  - 存什么？
- 记忆的层次结构：按照记忆的作用、存储时间、信息粒度和使用方式，将 Agent 的记忆划分为不同层次。
  - 便于理解和设计的记忆分类模型，并不是所有 Agent 框架都严格采用这四层结构,也不意味着它们必须按照固定的物理存储层级实现。
    - 工作记忆（Working Memory）：当前任务正在使用的信息 例如：当前对话、任务参数、中间推理结果、工具调用结果
    - 情景记忆（Episodic Memory）：过去发生过的具体事件和交互 例如：用户上次要求生成月度销售报告，最终采用了哪种格式
    - 语义记忆（Semantic Memory）：从经历中提取出来的事实、知识和概念，例如：用户负责订单系统，订单状态包括待支付、已支付、已取消
    - 程序性记忆（Procedural Memory）：如何完成某项任务的流程、规则和策略，例如：生成销售报告时，先查询数据，再计算指标，最后生成报告
  - 常用的记忆的层次结构实际上采用的是三个层次
    - 轨迹（Trajectory）：发生了什么？ 记录 Agent 与用户交互、执行任务的过程。核心：保留经历和过程，关注历史发生过程
    - User Long-term Memory（用户长期记忆）：用户是谁？从历史交互中提取值得长期保留的用户信息。核心：保留跨会话仍有价值的用户信息，关注用户长期特征和背景
    - Business State（业务状态）：事情进行到哪里了？记录业务对象当前的状态，以及业务过程中的关键变化。核心：保留业务事实及其当前状态，关注业务对象当前处于什么状态
- 四种记忆存储格式：
  - Simple Notes：把知识拆开存；独立事实保存，不需要额外的关系和复杂结构。
  - Enhanced Notes：把知识连起来存；多个事实构成完整的工作经历，保留叙述上下文有价值。
  - JSON Cards：把知识分类结构化存；通过分类和键值组织信息，支持相对明确的局部更新。
  - Advanced JSON Cards：把知识、来源、人物和关系一起存，可以记录人物身份、关系、来源背景和时间。。
- 可执行代码（User as Code）
- 认知科学中的记忆分类
- Mem0、Memobase 等记忆框架
- 记忆压缩与整理
- 隐私保护：日志脱敏

### 2.2 RAG 基础

### 2.3 知识的组织与检索

- 结构化索引：层次与关联
- 文件系统范式
- 知识增量更新

- 智能体化 RAG（Agentic RAG）
- 上下文感知检索
- 从数据集中提取结构化知识
- 多模态与参数化记忆

### 2.4 三类信息的边界

| 系统       | 主要解决的问题               | 示例                                   |
|------------|------------------------------|----------------------------------------|
| 用户记忆   | Agent 需要记住谁、记住什么   | 某员工负责订单系统，偏好使用 Java      |
| 企业知识库 | Agent 需要从哪里获取业务知识 | 公司的订单退款流程、技术规范、运维手册 |
| 当前上下文 | Agent 当前正在处理什么任务   | 员工正在咨询订单退款异常               |

这三类信息不能简单混在一起。用户记忆和多用户共享的企业知识库具有不同的权限范围、更新机制和使用边界。

## 三、企业级学习与实施计划

建议把第三章拆成六个实施阶段。每个阶段都包含理论学习、工程实现和验收结果。

### 阶段一：用户长期记忆系统

**学习重点**

1.  为什么 Agent 不能只依赖对话历史？
2.  Trajectory、Long-term Memory、Business State 有什么区别？
3.  情景记忆、语义记忆、程序记忆分别保存什么？
4.  Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards
    有什么区别？
5.  如何处理记忆新增、修改、删除和冲突？
6.  如何处理记忆的有效期、时间和来源？

**工程实现方向**

| 模块                 | 主要职责                 |
|----------------------|--------------------------|
| MemoryExtractor      | 从对话中提取候选记忆     |
| MemoryManager        | 管理记忆的生命周期       |
| MemoryRepository     | 持久化记忆               |
| MemoryRetriever      | 检索相关记忆             |
| MemoryUpdater        | 处理记忆更新和冲突       |
| MemoryContextBuilder | 将相关记忆注入当前上下文 |

以上是根据记忆管理职责划分的工程实现建议，并非书中规定的固定类结构。具体模块边界应在完成理论验证和现有代码分析后确定。

**阶段验收**

-   新会话能够找回之前会话中的信息。
-   能够识别用户明确表达的长期偏好。
-   能够处理同一事实的新旧变化。
-   不会把不同人物的信息混淆。
-   能够识别记忆适用条件和时间范围。
-   能够拒绝回答记忆中没有依据的问题。

**测试建议**

参考书中记忆能力评估实验：构造不同层次的记忆测试用例，分批更新记忆；后续测试时不再提供原始会话，只允许系统使用已经保存的记忆回答新问题。测试应覆盖记忆提取、保留、更新、检索和冲突处理。

### 阶段二：记忆治理与安全

**学习重点**

-   记忆压缩与整理
-   重复信息识别
-   事实抽象和规律提取
-   记忆保留与删除
-   敏感信息识别和日志脱敏

**工程实现方向**

-   记忆整理机制
-   记忆来源追踪
-   记忆时间管理
-   敏感信息识别
-   日志脱敏处理

特别注意：不能仅因为某条记忆访问频率低就直接删除。合同、长期约束等信息可能很少访问，但仍然具有保留价值。记忆整理策略应考虑信息价值、有效期、来源和删除规则。

### 阶段三：RAG 基础检索引擎

这是第三章技术含量较高的阶段。不要只接入现成向量数据库和检索组件，就认为
RAG 已经完成；需要理解检索原理并通过实验验证。

| 技术          | 需要掌握的内容                 |
|---------------|--------------------------------|
| Chunking      | 文档如何分块、重叠和保留上下文 |
| Embedding     | 如何将文本转换为向量           |
| ANN           | 如何进行近似最近邻检索         |
| TF-IDF        | 关键词权重计算                 |
| BM25          | 相关性评分                     |
| Hybrid Search | 稠密与稀疏检索融合             |
| Reranker      | 对候选结果重新排序             |

**结合当前 Ollama 模型环境的注意事项**

目前项目使用的本地模型包括：

-   `qwen3.5:4b`
-   `openbmb/minicpm5:2b`
-   `qwen3.5:9b`

目前尚未明确专门的 Embedding
模型。生成模型和嵌入模型承担不同职责，不能因为模型能够生成文本，就默认它适合生成检索向量。

进入这一阶段后，需要单独验证本地 Embedding
模型的选择、向量维度、中文检索效果和推理性能。

**工程验收**

-   自己实现 BM25，理解倒排索引和评分公式。
-   实现稠密检索。
-   实现混合检索。
-   比较不同检索策略的效果。
-   使用独立测试集评估 Recall@K、MRR、nDCG。
-   记录检索耗时和资源占用。

### 阶段四：企业知识组织

这一阶段从普通 RAG 走向企业知识管理。

**学习重点**

-   结构化索引
-   知识之间的关联关系
-   文件系统范式
-   知识增量更新
-   知识定期整理
-   上下文感知检索

**企业场景示例**

``` text
企业知识库
├── 技术规范
│   ├── Java开发规范
│   └── Python开发规范
├── 业务文档
│   ├── 订单管理
│   └── 退款管理
└── 运维文档
    ├── 部署手册
    └── 故障处理
```

当用户询问"订单退款失败应该如何排查"时，系统不仅要找到包含退款关键词的文本，还要理解：

-   文档属于哪个业务模块。
-   文档是否已经过期。
-   当前内容是否有适用条件。
-   是否存在关联的故障处理文档。
-   不同版本之间是否存在冲突。

### 阶段五：Agentic RAG

普通 RAG 的典型流程：

``` text
用户问题
   ↓
检索知识库
   ↓
获取相关文档
   ↓
LLM 生成答案
```

Agentic RAG 进一步让 Agent 参与检索决策：

``` text
用户问题
   ↓
Agent 分析问题
   ↓
判断是否需要检索
   ↓
选择检索策略
   ↓
执行检索
   ↓
判断结果是否足够
   ↓
必要时调整查询并再次检索
   ↓
组织最终答案
```

重点是研究书中"由 Agent 控制检索过程"的理论，而不是单纯增加几个
LangGraph 节点。

需要先验证理论，再决定哪些步骤需要模型决策，哪些步骤应该由确定性程序执行。

### 阶段六：综合集成与验收

最终让现有 Agent 同时具备：

1.  当前会话上下文能力。
2.  用户长期记忆能力。
3.  企业知识库检索能力。
4.  根据任务选择记忆或知识检索的能力。
5.  对检索结果进行判断和组织的能力。

目标是：用户不需要每次重新介绍自己的背景，Agent
也不需要把整个企业知识库塞进上下文，就能利用相关信息完成任务。

## 六、项目学习与开发的共同约束

1.  **理论先行：** 涉及技术架构的设计，必须先找到《深入理解 AI

2.  **不凭经验扩展：**

3.  **结合现有代码：**

4.  **代码必须有注释：**

5.  **先实验再选型：**

6.  **工程化验收：**
    不只验证功能可用，还要关注正确性、权限、安全、可观测性、性能和可维护性。

## 八、当前学习入口：实验 3-2——四种记忆存储格式的工程对比

**当前进度**

第三章已完成记忆层次、认知记忆分类，以及四种记忆存储格式的基础学习。当前进入实验 3-2：对 Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards 进行工程对比。

**当前阶段目标：** 不提前选定最终存储格式，也不直接开始实现完整的用户长期记忆系统；先通过统一测试条件，观察四种格式在实际记忆任务中的表现，为后续设计提供依据。

### 本阶段学习与实验步骤

1. 明确四种存储格式各自解决的问题、数据组织方式和适用场景。
2. 设计一组具有代表性的记忆样例与测试问题，确保四种格式使用相同的输入和评价条件。
3. 分别按照四种格式组织同一批记忆，记录记忆生成和更新过程中的差异。
4. 使用相同的问题测试记忆检索与回答表现，检查信息是否被遗漏、混淆或错误关联。
5. 对比各格式的结构表达能力、检索效果、更新维护复杂度和 Token 消耗。
6. 汇总实验结果，分析不同格式的优势、局限和适用边界。

### 实验过程中的约束

- 四种格式必须使用可比较的样例和问题，避免因测试数据不同而得出不公平结论。
- 区分实验观察结果与主观判断；没有实际测量的数据，不写成确定结论。
- 暂不引入向量数据库、RAG 或额外记忆框架，这些内容应在对应学习阶段再研究。
- 实验结束后先复盘结果，再讨论是否需要组合使用不同格式，以及项目第一版应采用什么方案。
- 当前尚未确认最终记忆存储格式，尚未进入用户长期记忆系统的正式编码阶段。

### 与现有项目的衔接约束

当前项目已经实现 Agent
对话历史管理和上下文压缩。因此第三章不能重新发明一套对话历史管理机制，需要明确长期记忆与现有历史管理之间的职责边界。

-   当前上下文：服务于正在进行的对话和任务。
-   长期记忆：保存跨会话仍然有价值的信息。
-   企业知识库：提供组织共享、可检索且受权限约束的业务知识。


## 九、实验代码实施与学习记录规范

### 9.1 实验实施原则

第三章所有实验代码遵循以下原则：

1. 以书中实验目的、原始顺序和评价方式为准。
2. 结合当前 Ollama、LangChain 和 Python 技术栈进行必要适配。
3. 采用精简学习模式：快速理解当前目标，集中完成当前实验步骤所需实现，再检查实际运行结果。

6. 实验实现与正式项目实现保持边界。

### 9.9 Advanced JSON Cards 理论学习阶段总结与学习顺序纠偏（截至 2026-11-25）

#### 本轮已讨论的知识点

本轮继续学习 Advanced JSON Cards 的字段语义、信息组织和事实消歧，已讨论：

1. **相较基础 JSON Cards 的信息补充**：基础 JSON Cards 主要通过分类路径和键值保存结构化事实；Advanced JSON Cards 进一步补充事实主体、主体关系、来源背景和时间等上下文信息。
2. **`person`**：标识这条信息描述的主体是谁，不等同于当前用户本人。
3. **`relationship`**：描述信息主体与用户之间的关系，不能与 `person` 混为一谈。
4. **`backstory`**：记录信息来源、产生背景、保存原因及已知的变化过程。它可以帮助理解事实，但不等于自动保存了每个历史版本，也不能凭空补充对话中没有出现的动机或原因。
5. **创建时间与事实时间**：讨论了卡片创建时间与事实实际生效时间的区别，并用 Valid Time / Transaction Time 的例子练习事实更正。该概念用于辅助理解时间语义，不应误写成书中要求所有卡片必须具备的固定字段。
6. **人物与事实消歧**：同名人物可能对应不同主体；同一句话包含多个主体时，应根据各自事实拆分和关联，避免将不同人的信息混在同一张卡片中。
7. **业务对象身份与更新**：同一笔业务的连续修改应关联到同一业务对象；稳定的卡片标识应表达业务对象身份，而不是简单使用每次变化的业务编号。该讨论属于设计理解，不代表书中规定了唯一 ID 算法。
8. **来源忠实性**：`backstory` 只能记录来源明确支持的背景；不能把推测出来的修改原因写成事实。
9. **Advanced JSON Cards 的能力边界**：增加背景、主体、关系和时间信息可以改善理解与消歧，但不自动构成完整的历史版本审计，也不能替代原始对话证据。

#### 本轮进一步明确的知识点

在前述字段语义和事实消歧讨论的基础上，进一步明确了以下内容：

1. **Advanced JSON Cards 与原始对话的边界**
   - Advanced JSON Cards 保存经过提取和组织的结构化事实及其背景信息，不等于完整的原始对话记录。
   - 卡片只能提供实际保存的信息，不能保证还原原始对话中的所有表达、修改细节和上下文。
   - 当问题需要核实卡片未保存的对话细节时，需要结合原始对话检索获取补充证据。
   - 这说明结构化记忆与原始对话检索承担不同职责，但本轮仅讨论其概念关系，尚未正式开展 Contextual Retrieval 学习和实验。

2. **`backstory` 与事实有效时间**
   - `backstory` 可以保存事实来源、产生背景和已知变化过程。
   - 当背景信息明确包含事实的生效时间时，可以据此理解事实的时间范围。
   - 如果原始信息没有提供明确时间，不能仅凭背景描述推断准确的生效日期。
   - 需要区分信息记录时间、事实实际生效时间和事实变化时间，不能将它们直接等同。
   - 记录时间与事实有效时间的区分属于辅助理解，不代表书中要求增加固定的 Valid Time / Transaction Time 字段。

3. **业务对象标识的稳定性**
   - 同一业务对象在整个生命周期内应保持身份标识稳定。
   - 对象属性发生变化，例如转账金额、日期或其他信息更新，不应导致业务对象身份发生变化。
   - 稳定标识用于关联同一对象的连续变化，而不是将每次属性修改视为一个全新的对象。
   - 具体标识生成算法属于后续工程设计问题，书中没有规定唯一实现方式。

以上内容属于理论讨论和设计理解，尚未通过 Advanced JSON Cards 实验验证，也不代表当前项目已经实现相应能力。

以上为理论讨论和示例推演，尚未开展 Advanced JSON Cards 的代码实现或实验运行。
