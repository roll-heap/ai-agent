### 4.3 Advanced JSON Cards 实践记录

**知识目标：** 使用结构化 JSON 卡片表达用户记忆，并通过管理器维护记忆数据。

**管理器职责：** `AdvancedJsonCardMemoryManager` 负责卡片的新增、更新、删除、查询和 JSON 持久化。卡片通过 `category + card_key` 组织和定位；卡片字段承载记忆内容，`_metadata` 记录管理信息。

**独立实践技术：**

| 技术 | 用途 |
|---|---|
| OpenRouter | 提供远程模型 API |
| OpenAI Python SDK | 调用 OpenRouter Chat Completions 接口 |
| Function Calling | 让模型选择记忆管理工具并生成调用参数 |
| 自定义 ReAct 循环 | 执行工具调用，并将工具结果反馈给模型 |
| AdvancedJsonCardMemoryManager | 执行记忆卡片操作及 JSON 持久化 |

实践模型：`baidu/ernie-5.5-flash-preview:free`。模型服务和免费额度可能变化；密钥仅保存在本地配置中，不得写入项目文档或提交到 Git。

**接入工具：**

- `add_memory`：新增记忆卡片。
- `update_memory`：更新已有记忆卡片。
- `delete_memory`：删除已有记忆卡片。

**核心调用链：**

```text
用户输入
  → Agent 请求模型
  → 模型返回 tool_calls
  → Agent 解析工具名称和参数
  → Agent 调用记忆管理器
  → Agent 将工具执行结果按 tool_call_id 回传模型
  → 模型根据工具结果继续处理
  → Agent 输出最终回答
```

模型负责判断是否需要调用工具并生成参数；Agent 负责调度、执行工具和反馈结果；记忆管理器负责数据校验、实际操作及持久化。工具调用成功与否应以工具执行结果为准，不能仅凭模型发出 tool_calls 就认定操作成功。

**时间字段处理：**

- `date_created`：卡片业务字段。新增时由程序/管理器生成，不让模型猜测创建时间；更新时保留原值。
- `_metadata.created_at`：管理器记录的卡片创建元数据。
- `_metadata.updated_at`：管理器记录的最近更新时间。
- 三者语义不同，不应混用。历史数据中的错误 `date_created` 不会因修改生成逻辑而自动修复，需单独评估和处理。

## 六、关键技术结论与设计决策

### 6.1 认知科学中的记忆类型

| 类型 | 核心含义 | 典型内容 |
|---|---|---|
| 情景记忆（Episodic Memory） | 记录具体发生过的事件，保留事件背景和经历细节 | 用户上周在某餐厅用餐 |
| 语义记忆（Semantic Memory） | 从经历中抽象出的相对稳定的事实、知识或偏好 | 用户长期偏好意大利菜 |
| 程序记忆（Procedural Memory） | 记录完成某类任务的方法、步骤或行为模式 | 用户点餐时通常先选主菜，再选择饮料 |

**使用边界：**
- 单次行为只能作为一条具体经历，不应直接推断为长期偏好；稳定偏好需要有足够的事实依据。
- 程序记忆描述任务如何完成，不意味着 Agent 可以跳过必要的权限检查、用户授权或确认。
- 三种记忆类型关注信息的性质，不等同于具体的存储位置或数据格式。

### 6.2 不同记忆分类维度的关系

| 分类维度 | 回答的问题 | 本专题中的例子 |
|---|---|---|
| 记忆层次 | 信息存在哪里、服务于什么范围？ | Trajectory、User Long-term Memory、Business State |
| 存储格式 | 信息如何组织和表示？ | Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards |
| 认知类型 | 信息属于哪种记忆？ | 情景记忆、语义记忆、程序记忆 |

这三个维度相互独立，不是一一对应关系。例如，“用户长期偏好意大利菜”属于语义记忆，可以保存在 User Long-term Memory 中，并采用文本笔记或 JSON Cards 表达。

### 6.3 工作记忆与运行轨迹（扩展知识）

工作记忆（Working Memory）指当前任务中被临时激活、筛选并实际使用的信息集合；运行轨迹（Trajectory）则记录 Agent 运行过程中产生的消息、动作和结果等过程信息。二者不能等同：轨迹是过程记录，工作记忆是当前任务所需的信息集合。

### 6.4 其他技术结论与设计决策

- 用户经历变化时，旧经历不能继续作为当前事实；应保留历史并明确当前状态。该要求已确认，但尚未在当前数据模型和管理器中实现。
- `backstory` 只能记录来源支持的背景，不能编造人物动机、修改原因或事实时间。
- `person` 表示事实主体，`relationship` 表示主体与用户的关系。
- 创建时间、事实有效时间和事实变化时间不能混为一谈。
- Advanced JSON Cards 不等于完整历史版本审计，也不能替代原始对话证据。
- 同一业务对象的属性变化不应自动改变对象身份；具体标识算法尚未确定。
- 在 ReAct 工具循环中，模型发出工具调用请求不等于工具执行成功；Agent 必须执行工具，并将带有对应 `tool_call_id` 的执行结果反馈给模型。
- 工具参数需要在执行边界进行校验，不能只依赖模型遵循提示词或 JSON Schema。
- 新增记忆时，系统生成创建时间；更新时保留原始创建时间，避免模型生成或覆盖不可信时间。
- `date_created` 是卡片字段，`_metadata.created_at` 和 `_metadata.updated_at` 是管理器元数据，必须按各自语义使用。
- 本轮 OpenRouter + Function Calling + 自定义 ReAct 实现属于独立实践，不应表述为书籍配套代码或项目主线已集成能力。
- 上述讨论结论不应描述为书籍规定的固定字段或当前项目主线代码能力。

### 6.5 Mem0：记忆提取与检索

**配套代码与职责边界：**

- `AgentContext` 管理当前运行中的会话状态、用户标识、Agent 标识和对话历史；Mem0 管理跨会话长期记忆。二者互补，不能相互替代。
- `Mem0Agent` 协调记忆检索、Prompt 组织、模型生成和记忆写入；Mem0 SDK 执行记忆提取、存储和检索。
- 作者配套代码中的 `main.py` 负责交互入口，`config.py` 负责模型、后端和向量存储配置，`KimiK3Client` 负责调用聊天模型。

**检索与写入闭环：**

```text
用户输入
  → Mem0Agent.process_turn()
  → memory.search(query, filters, top_k=5)
  → 将检索结果组织为 System 消息，并与会话历史、当前问题组成模型输入
  → LLM 生成回答
  → memory.add(本轮 user / assistant 消息)
  → Mem0 提取并保存记忆
```

- `search()` 根据当前用户输入检索相关记忆；配套代码通过 `user_id` 和可选的 `agent_id` 传入过滤条件，最多取回五条候选记忆。
- Mem0 不直接生成面向用户的回答。Agent 将检索结果注入模型上下文，再由 LLM 结合当前问题生成回答。
- `add()` 提交本轮用户消息和助手回答，由记忆框架提取值得保留的事实。作者 README 将当前配套代码描述为 Mem0 v3 的 ADD-only 提取模式：新事实追加保存，不应理解为自动覆盖旧事实。
- 新旧事实可能同时存在；后续回答需要结合时间、语义和具体适用条件判断，不能只凭“最新检索结果”或记录顺序认定事实有效。
- 配套代码的 metadata 包含 session_id、turn 和 timestamp；这些元数据不能直接证明每条提取事实都具有独立、准确的事件发生时间。

**配置与管理边界：**

- 本地模式使用 Mem0 OSS 和 Chroma；作者配置中向量库默认路径为 `./data/chroma_db`。聊天模型通过 OpenAI 兼容接口连接 Moonshot；本地默认 Embedder 使用 OpenAI Embeddings，因此本地存储不代表模型和嵌入服务也都在本机运行。
- Cloud 模式通过 `MemoryClient` 访问 Mem0 Cloud。配套代码没有向云端客户端传入本地的 LLM、Embedder 和 Vector Store 配置，不能据此推断云端内部具体存储实现。
- `get_all()` 用于列出指定范围内的记忆，`history(memory_id)` 查询单条记忆的历史，`delete(memory_id)` 删除指定记忆；它们与按查询相关性召回的 `search()` 用途不同。
- 配套代码的删除包装层只传入 memory_id，没有展示 user_id / agent_id 级别的权限校验。多租户应用必须在应用层验证操作者是否有权管理该记忆；不能把模型或 SDK 返回的记忆 ID 当作授权凭据。
- 以上是作者配套代码的实现观察，不代表 Mem0 所有版本或云端服务内部实现的完整保证。

**本地独立实践与验证：**

- 本地环境：macOS M1 16GB、Python 3.12.12，使用 `mem0ai==2.2.1`、`ollama==0.6.3`、`chromadb==1.5.9`；Chroma 作为本地持久化向量库，Embedding 使用 Ollama `qwen3-embedding:4b`（2560 维），聊天模型通过 OpenAI 兼容接口调用 DeepSeek。
- 在 `infer=True` 条件下，DeepSeek + Mem0 成功从用户信息中提取三条记忆，均以 `ADD` 事件写入；随后按相同用户及 Agent 过滤条件执行语义检索，成功召回这三条记忆，进程正常退出。
- 此次结果验证了当前配置下 Mem0 的自动提取、向量存储和语义检索闭环；不代表其他模型或配置具有相同提取效果。
- 此前使用本地 Qwen2.5:3B 进行自动提取时，当前模型与 Prompt 条件下未得到有效记忆结果；`infer=False` 的基础写入和检索可用。该观察不能推导为该模型在所有场景下均不支持记忆提取。
- Chroma 提示不支持 keyword search，因此本次检索仅使用语义相似度，未启用 BM25 混合评分。PostHog 多实例及 Typer/Click 弃用提示不是本次功能验证的阻塞错误。
- 本地脚本位于用户工作区 `book/chapter3/storage_memory/memobase/mem0_local_demo.py`；该本地实践不等于 `chapter3` 分支中的同名文件已同步更新。当前分支源码仍需按实际仓库内容单独判断，不能把本地配置或验证结果描述为仓库实现。



### 6.6 Memobase：用户画像与事件记忆

**两类记忆：**

| 类型 | 关注点 | 示例 |
|---|---|---|
| Profile | 用户相对稳定的属性、习惯和偏好，按主题与子主题组织 | 用户偏好简短回答、从事后端开发 |
| Event Memory | 用户在特定时间经历的事件及其相关信息 | 上周将项目预算确定为 50 万 |

- Profile 关注“用户通常是什么样的”，作者示例从 SDK 返回对象读取 `topic`、`sub_topic`、`content`。
- Event Memory 关注“用户在什么时候经历了什么”，作者示例读取 `created_at`、`event_data.event_tip` 和 `event_data.event_tags`。
- `created_at` 是示例代码读取的事件记录创建时间，不应未经核实就等同于事件实际发生时间；`event_data` 也可能为空。
- 同一长期偏好的不同表达仍属于 Profile 候选，不会因为表达发生在不同轮次就自动变成 Event。一次特殊场景下的临时选择应作为事件理解，不能直接覆盖长期偏好。

**缓冲批处理与查询接口：**

```text
insert → flush → profile / event / context
```

- `insert()` 将对话写入用户缓冲区，本身不代表记忆已经提取完成。
- `flush()` 触发对缓冲区内容的批量记忆提取；作者示例使用 `flush(sync=True)` 等待处理完成。
- 书籍说明缓冲批处理可在缓冲区达到指定规模、会话空闲达到设定时长或显式触发时执行。示例中的显式 flush 不足以证明 SDK 默认阈值或具体后台触发策略。
- `profile()` 读取结构化用户画像，`event()` 读取事件记忆，`context()` 获取可供应用使用的记忆上下文字符串。
- 缓冲批处理将多条对话集中处理，减少逐轮触发记忆提取的开销；在提取完成前，查询结果不应被当作已包含最新对话。

**与 Agent 的集成边界：**

- 作者的 `profile_demo.py` 是真实 Memobase Python SDK 的演示，负责连接 Memobase 服务、写入对话、触发提取并读取 Profile / Event / context；它本身没有实现完整的 Agent 问答链路。
- 在完整 Agent 应用中，应用可调用 `user.context()` 获取记忆上下文，再将其与系统提示词和当前问题共同组织为模型输入。记忆框架负责记忆处理与召回，Agent 负责按当前任务选择和使用这些信息。
- 作者另有受 Memobase 启发的手写记忆 Agent，使用自定义 MemoryStore 和本地持久化实现多种记忆处理机制；它不是 Memobase SDK 的内部实现，不能将两者的能力或代码混为一谈。
- 本地自托管 Memobase 服务已部署，Python SDK 已成功连接并完成基础调用验证。该状态不代表 `insert()`、`flush()`、`profile()`、`event()`、`context()` 等所有接口均已逐一验证；具体范围以用户实际运行记录为准。

### 6.7 隐私保护：日志脱敏

**目标与风险：**

Agent 日志可能包含用户输入、模型输出、System Prompt、上下文记忆、工具参数与结果、异常堆栈等内容。日志可能进入日志平台、监控、数据分析或模型评测流程，因此需要在持久化前识别并处理敏感信息，降低 PII、账户信息和凭据泄露风险。

**脱敏方案：**

| 方案 | 适用范围 | 优势与局限 |
|---|---|---|
| Regex（规则匹配） | 格式相对固定、可明确识别的内容，如手机号、邮箱、API Key、JWT、银行卡号等 | 结果确定、速度快、可离线执行；难以理解自然语言语义，可能漏掉非标准表达 |
| Local LLM（本地模型） | 需要结合上下文理解的敏感内容，如自然语言中描述的个人隐私或医疗信息 | 能识别部分语义型敏感信息；受模型能力和提示词影响，可能漏识别、误识别或输出不符合预期的替换文本 |
| Hybrid（混合方案） | 同时存在固定格式和语义型敏感信息的日志 | 规则处理确定性较高的模式，模型补充语义识别；需要协调处理顺序、冲突和性能成本 |

手机号、银行卡号等通常具有相对稳定的格式或校验规则，适合优先使用 Regex；自然语言中的密码提示、健康状况或其他隐私描述依赖上下文语义，单纯正则难以可靠识别，可考虑由模型辅助判断。Regex 也可以结合 Luhn、身份证校验码等校验逻辑减少误判，但校验通过不等于该数据在当前业务场景中必然属于敏感信息。

**识别质量指标：**

- Recall（召回率）= TP / (TP + FN)，衡量实际敏感信息中有多少被识别出来；Recall 低意味着漏掉的敏感内容较多。
- Precision（精确率）= TP / (TP + FP)，衡量被识别为敏感的信息中有多少确实敏感；Precision 低意味着误判较多。
- 只追求高 Recall 可能导致大量普通内容被误脱敏，降低日志可读性和故障排查价值。因此应同时关注 Recall、Precision、普通文本保留情况及处理耗时。

**日志处理位置与可观测性：**

推荐在日志持久化之前执行敏感信息识别和脱敏：

```text
Agent 执行
  → 生成日志事件
  → 敏感信息识别
  → 脱敏处理
  → 日志持久化
  → 日志平台 / 监控 / 分析
```

脱敏时应尽量保留 request ID、Trace ID、工具名称、执行状态、错误类型、耗时和调用链路等排障所需信息，避免把整条日志无差别删除。日志脱敏只保护进入该日志链路的数据，不代表模型上下文、记忆数据库、工具参数或其他持久化数据也自动得到保护；这些数据路径需要分别定义权限、保留和脱敏策略。

**本地模型与数据边界：**

本地运行 Ollama 并不自动意味着整个脱敏流程都在本机完成。如果本地模型不可用时系统回退到 OpenRouter 等云端模型，原始日志或待识别文本可能离开本机。生产环境需要明确云端回退是否允许、发送前是否先做规则脱敏、失败时是否阻断或降级，以及密钥和日志的访问控制策略。

**配套项目样例结果（作者 README 报告，非本项目实测）：**

作者在同一组 12 条标注样例上报告：Regex 平均 Recall 为 50.0%、残留敏感值 9 个；LLM 平均 Recall 为 69.4%、残留敏感值 3 个；Hybrid 平均 Recall 为 77.8%、残留敏感值 2 个。这些数字仅反映作者配套样例和其运行条件，不代表通用性能结论，也不是本项目的运行结果。
